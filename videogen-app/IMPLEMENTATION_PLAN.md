Ворота пройдено (+24 тести, плюс глобальна перевірка процесів-сиріт
наприкінці кожного прогону):
* зависання (0 % CPU) → stall за ~1 с; livelock (100 % CPU без кадрів) → виявлено;
* hard timeout спрацьовує навіть при постійному прогресі;
* онук-процес вбивається разом із деревом; процес, що ігнорує `q` і SIGTERM, — теж;
* спочатку пробується м'яке завершення `q` (перевірено кодом виходу);
* скасування — менш ніж за 5 с, з видаленням незавершеного файлу;
* 50 МБ у stderr без взаємоблокування; ріст файлу без блоків прогресу не
  вважається зависанням;
* справжній FFmpeg: монотонний прогрес до 150/150 кадрів; скасування посеред
  кодування — процес зник, файл видалено;
* реєстр процесів порожній після кожного тесту; жодного дочірнього процесу
  наприкінці сесії тестів.

**Обмеження:** код Windows Job Objects написано за документацією WinAPI, але
в цьому Linux-середовищі його неможливо виконати. Він буде перевірений у
CI-збірці на `windows-latest` (PHASE 9). До цього на Windows діє запасний
механізм — psutil-вбивство дерева, перевірене тут.

|---|---|

| `core/pipeline.py` | усі етапи; повторне використання перевірених артефактів; атомарна публікація з SHA-256 і записом наміру наперед; архів в окремому процесі під watchdog; PARTIAL для пропущених і відновлених зображень |
| `core/engine.py`, `engine_main.py` | команди, пошук завдань, черга, відновлення після збою, ETA, пересилання журналу в GUI, heartbeat, вихід при зникненні GUI, **блокування одного екземпляра** |
| `providers/base.py`, `providers/fake.py` | MODE B: інтерфейси провайдерів, кеш за хешем (повтор не генерує й не оплачує ті самі ресурси вдруге), тестові провайдери |

Вибір реалізації руху: на спайку `zoompan` по полотну, збільшеному вдвічі,
дає 150 кадрів 1080p приблизно за 3,6 с у цьому контейнері, а фільтр без
кодування працює на ~110 кадр/с (основний час іде на кодування);
кількість кадрів точна, `xfade` дає чистий перехід (кадр 0 — повністю
попереднє зображення, кадр T — повністю нове).

Ворота пройдено (**434 тести**, +28), реальний FFmpeg:
* повний job з Unicode-назвою: точна кількість кадрів, архів із вхідними
  файлами, жодного залишкового файлу у workspace, жодного процесу;
* 9:16 з горизонтальними фото; PARTIAL із суфіксом ` [PARTIAL]`, події
  `ImageSkipped`, повідомлення «Не вдалося використати зображення №2…»;
* пакет: добрий / битий аудіо / усі зображення биті / немає аудіо / добрий
  → 2 SUCCESS + 3 FAILED, битий аудіо без повторів;
* STOP посеред рендеру → CANCELLED, жодного файлу в output;
* PAUSE на межі фрагмента → RESUME → SUCCESS;
* зависання і падіння FFmpeg на фрагментах → рівно одна повторна спроба,
  FAILED, діагностичний знімок;
* верифікація не пройшла → рівно одна повторна спроба, у output нічого;
* помилка архіву → FAILED(ARCHIVE), відео лишається; ліміт розміру архіву;
* FFmpeg недоступний; нестача диска (перевірка до старту, автопауза пакета);
  нестача ресурсів (обмежене очікування);
* MODE B з тестовими провайдерами; повторний запуск бере все з кешу;
* наявний файл користувача з тим самим іменем не перезаписується;
* **вбивство процесу (SIGKILL) посеред рендерингу** → перезапуск →
  INTERRUPTED → Resume → рендеряться лише незавершені фрагменти; вже готове
  відео іншого job не змінено (перевірено SHA-256).

Знайдені під час фази проблеми та рішення:
1. дочірні процеси в режимі spawn (єдиний режим на Windows) повторно
   виконують головний модуль: без захисту `if __name__ == "__main__"` кожен
   дочірній процес запускав би новий Engine → обов'язкові `freeze_support()`
   і захист у `main.py` (PHASE 6/9);
2. два Engine на одних даних псують стан одне одному → додано блокування
   одного екземпляра (`engine.lock`, знімається ОС автоматично при падінні);
3. повідомлення журналу про етап не містило назви етапу.

**Семантика повторної спроби** (уточнення §11): «чистий workspace» означає
видалення всіх тимчасових і неперевірених файлів; нормалізовані зображення та
фрагменти, що пройшли перевірку кількості кадрів, зберігаються і
використовуються повторно. Так повтор після зависання на фрагменті 37 не
рендерить заново фрагменти 1–36.

Windows обмеження не діє.
